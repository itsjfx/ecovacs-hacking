# notes for DEEBOT T9+ (DLX13) on RV1126

These notes are from a retail **DEEBOT T9+ (DLX13)**, AU, on firmware `2.5.5`.
Written in the same spirit as `x1_omni.md` — mostly corrections and extensions to
what is already around, because the T9 line turns out to be **two different SoCs**
depending on firmware train.

Credit for the groundwork to Dennis Giese / braelynn (`robotinfo.dev`,
dontvacuum.me) and to `x1_omni.md` — the U-Boot `Ctrl+C` and `eco_passwd` sections
here just bend those to this board.

## info on the T9+

* Rockchip **RV1126**, 4x ARM Cortex-A7, **`armv7l` (32-bit)**
* `Linux deboot 4.19.111 #7 SMP PREEMPT Thu May 6 15:54:25 CST 2021 armv7l GNU/Linux`
* 512 MB DDR3 (924 MHz final), 512 MB NAND (`FLASH ID: 98 dc 90 26 76 16`,
  Rockchip SFTL 5.0.55)
* PMIC/audio: RK809 (`rk809-codec`); SoC serial appears as `chip_id:112600,0`
* `/etc/fw.manifest`:
  `{"release_date":"2021-06-01","product":"rv1126_zj2010","hw_ver":"1.0","fw_ver":"2.5.5"}`
* cloud class `dj8zpr`; OTA served from `portal.ecouser.net`
* "platform" in the OTA query is `QJ2077`

### the T9 chassis shipped on two SoCs

| firmware | SoC | arch | kernel | `product` | class family |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `1.x` | Rockchip PX30 | aarch64 | `4.4.185` | `zj2010_t9` | `lhbd50` |
| `2.x` | Rockchip **RV1126** | **armv7l** | `4.19.111` | `rv1126_zj2010` | `dj8zpr` |

Practical consequence: 32-bit vs 64-bit changes which prebuilt binaries you can
drop on it. An `aarch64` build (e.g. `ValetudoEV`'s `build_aarch64`) will not run
on the `2.x` units.

## debug port

Same 2x4 2.00 mm JST (PHDR-08VS) in the dustbin bay, above the Micro-USB. On this
unit, looking down with the front of the robot away from you:

* top row, 3rd from left = `GND`
* bottom row, 1st from left = robot `TX`
* bottom row, 2nd from left = robot `RX`

`115200 8N1`. Meter `GND` against the Micro-USB shell before connecting, since
some boards are rotated 180 degrees.

The Micro-USB port is OTG only (`Rockusb` / U-Boot `ums`). `/etc/rc.conf` ships
`!adbd.sh`, so no gadget appears in normal operation. Starting
`/etc/rc.d/adbd.sh start` creates a USB gadget `2207:0011` (ADB + mass storage)
and listens on ADB TCP `5555`.

## root password (`eco_passwd`)

`/etc/rc.d/pre_boot.sh` copies `/etc/passwd-bk` to `/tmp/root/etc/passwd`
(`/etc/passwd` is a symlink into `/tmp`) and runs
`eco_passwd -f /etc/conf/eco_passwd.conf`.

The product key comes from `/etc/fw.manifest`, so **it changed with the SoC**:

```
1.x  zj2010_t9
2.x  rv1126_zj2010      <-- not in the public calculator lists at time of writing
```

Computation as published, base64 of the ASCII `sha256sum` text, **truncated to 8
characters** before `echo "root:%s" | busybox chpasswd`:

```
pw = base64( sha256_hex(product + "d4:3d:7e:fa:12:5d:C8:02:8F:0A:E2:F5"
                        + sn[-8:] + "\n") + "  -\n" )[:8]
```

The 20-character SN lives at offset 1 MiB of the `sys` partition. Verified by
logging in on the console.

## U-Boot

```
U-Boot 2017.09-g24b6d4d #richard (May 07 2021 - 16:56:33 +0800)
board=evb_rv1126
bootdelay=0
SecureMode = 0
```

`bootdelay=0` but `Ctrl+C` is still catchable if you burst `0x03` starting from the
first SPL/DDR byte (a loop that writes `\x03` every few ms as soon as any byte
arrives works reliably). If you miss it, nothing bad happens — the kernel just
starts.

From `=>`, this drops you into an unauthenticated shell in about a second, which
is handy for reading `/etc/fw.manifest` before you know the product key:

```
setenv bootargs "${bootargs} init=/bin/sh"
boot
```

`exec /sbin/init` afterwards brings up the normal system.

## partitions

GPT, 512-byte LBAs, `512 MB` NAND. Same layout as the PX30 T8 AIVI:

| part | start | size |
| :--- | :--- | :--- |
| `uboot` | `0x4000` | `0x2000` |
| `trust` | `0x6000` | `0x2000` |
| `mx` | `0x8000` | `0x2000` |
| `my` | `0xa000` | `0x2000` |
| `sys` | `0xc000` | `0x1000` |
| `boot1` | `0xd000` | `0x3000` |
| `rootfs1` | `0x10000` | `0x23000` |
| `boot2` | `0x33000` | `0x3000` |
| `rootfs2` | `0x36000` | `0x23000` |
| `data` | `0x59000` | `0x8efdf` |

* A/B boot flag: `sys` offset **0** holds `boot_mode1` / `boot_mode2`; the first
  sector is otherwise all zeros, and U-Boot falls back to `boot_mode 1` when the
  comparison fails.
* Boot counter: `5` written at 512-byte block **256**.
* SN and IoT credentials live below 1 MiB of `sys`.
* `rootfs` is unsigned SquashFS mounted read-only; no dm-verity, no signature
  check. `/data` is ext4.

## persistence gotcha: `!autostart.sh`

The widely-cited "drop a script in `/data/autostart`" recipe **does not work by
default** on these images. `/etc/rc.conf` ships `!autostart.sh`, and
`/etc/rc.sysinit` skips any daemon whose entry starts with `!`:

```sh
for daemon in ${DAEMONS}; do
  case ${daemon:0:1} in
     '!') continue;;     # Skip this daemon.
```

Observed in three separate T9 SquashFS images (`lhbd50` 1.4.8, `fqxoiu` 1.6.3,
`dj8zpr` 2.5.5) — all `!autostart.sh`. Check your own `rc.conf` before relying on
that path.

Two approaches that do survive a `/data` wipe / factory reset:

1. bind-mount a modified script or a stub over the file in the read-only
   SquashFS at boot (mounts need no write access to the underlying filesystem,
   and evaporate on reboot, so they are trivially reversible);
2. bake the change into both A/B `rootfs` slots (factory reset only clears
   `/data`).

## OTA

Chain is entirely shell scripts under `/etc`:

```
crond (0 * * * *) -> autoOTA.sh -> start_ota.sh -> medusa FW plugin
   -> download_fw_hook_v3.sh -> fw_upgrade.sh
```

`fw_upgrade.sh` writes only `boot1/2`, `rootfs1/2` **and the `sys` boot flag** —
it never touches `uboot` or `trust`, so U-Boot stays reachable after any OTA.
Each stage can be neutralised by bind-mounting a stub over it.

## `fw_target` and the `sl` section

`/usr/bin/fw_target` still uses the same XOR-`0x55` obfuscated format string as
the PX30 build:

```
ZWNvX2Z3X3RhcmdldCA%s1jdSAt%sbyBtYW4%dy5iaW4%s%x825xx%s
  args: "ECO-PT", <platform>, <section type>, "", <section len>, "jeff-hk@126.com"
```

Note the `2.7.0` OTA package for this class does **not** decrypt with a
`px30`-shaped key, and section 0's header byte 2 differs between trains (`0x39`
on `1.4.8` vs `0xf1` on `2.7.0`). The format string is unchanged, so the
difference is most likely the cipher/mode or the section-type nibble rather than
the platform token. Unresolved: the `2.7.0` package needs a key variant that this
format string alone does not produce.

The OTA bundle has a `sl` section (35,964 bytes) separate from `mcu`. That is the
**structured-light / TrueDetect 3D module** firmware, flashed via
`/etc/conf/medusa/sl_ota_hook.sh` -> `mdsctl slota` on `/dev/ttyS3`. The module
is present on this SKU (`/opt/sl.bin`, `/data/sl-bk/`, `/linelaser/*` and
`/setting/SlOnOff` topics); there is **no camera** (no `/dev/video*`, no
`isp`/`mipi`/`vip` platform devices).

## software

Same architecture as the X1 notes: `/usr/bin/deebot` is a ROS Melodic node
(`/node`) that loads `liberos_node_*.so` plugins from `/usr/lib/node/` via
`/etc/conf/dxai_node.json`; `medusa` is the cloud/app bridge (`/ROSNODE`) and is
driven by `mdsctl`. Notable libraries on this unit: `libDeebot.so` (planner entry
points `robot_clean_init_plan`, `robot_clean_run`), `libSlTrack.so`
(`sl::SlMove::ErgMapRunInit/ErgMapRun`), `libroom_analyze.so`
(`RoomAnalyze::SeedFilling`, `AreaFillInfo`, `getErgodicRoomSequence`).
Coverage rasters are persisted to `/data/FILES/autosave/`
(`regionTraceData_backup.bin` 1200x1200, `ergodicMap.bin` 800x800,
`ergodic.json`), which is handy for offline analysis.
